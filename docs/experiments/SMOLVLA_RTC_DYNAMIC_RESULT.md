## 1. 接入方式：传入真实承诺前缀，不修改动作起始行

`RTCPrefixOwner.submit`在原队列begin时创建`RTCRequest`，携带请求身份、独立复制的当前观测、归一化CPU float32旧动作尾段及来源请求ID。模型线程不再只收到裸观测，控制器继续消费不会改变已提交的前缀快照。使用归一化动作，不把后处理环境命令当成模型条件。

`DynamicPrefixRTC`用原CPU公式生成delay0..8、有效horizon1..10的精确权重表；每请求刷新固定地址设备权重和50x7零填充前缀。捕获代码的canonical key虽为(3,10,50)，实际使用的值是W(本请求delay,min(真实长度,10),50)，不是把运行中的delay固定为3。保留原完整Jacobian/VJP和7D有效维度掩码，不改原RTCProcessor.denoise_step与十步积分公式。

`DynamicRTCPredictor`只在rtc_async臂传入真实旧前缀和预计delay；两对照关闭引导。三臂使用同一动态Graph runtime，并在每个episode控制开始之前准备无前缀/有前缀两图。每请求重新处理当前双相机、状态和语言，并生成新的专用随机噪声。禁止控制中重捕获或静默使用慢路径。

原`control_loop`、`InferenceOwner`的服务/接收/关闭方法及`RTCExecutionQueue`保持字节不变。结果仍只在环境返回边界安装：

`新块起始行 = 实际接管动作索引 - 请求观测动作索引`。

预计delay用于生成时的前缀权重，实际消费量用于一次trim；二者分别记录，不互相冒充。没有保序row0队列、身份特例、未来观测、训练或真机操作。

## 4. 动态前缀确已生效；贴合仍不等于任务正确

全部79个有前缀RTC请求都核验了begin时旧计划来源、归一化尾段、独立载荷、实际送入模型的前缀、零填充值及精确权重。没有仅打开配置却漏传前缀。本批闭环的前缀长度实际均为30；预计delay随请求变化为7、4、5，实际消费主要3步、少数4步。变长前缀覆盖来自E-RDC1接口探针，不能说本批闭环观察到了225种组合。

正式审计后，仅对保存数组作描述性分析，新增模型与环境均为0。10个身份的第一次重规划（request2）在RTC与无RTC之间拥有相同的8项非前缀输入、噪声与旧归一化前缀。对实际消费步数范围内的旧前缀，平均MSE由0.143369330下降到0.002473201，10/10均下降。这不是专家动作误差，也不是新的接纳门。

例如7/18的该指标由0.090818410下降到0.001671643，但RTC最终失败、无RTC成功。可见前缀条件确实改变并约束了模型输出，但局部贴合无法替代终局任务保持。

另一个待检验现象：79次RTC接管中78次预计delay大于实际消费，1次相等，无低估；平均多1.430380步。第一轮重规划均预计7步，其中9次实际3步、1次4步。这表示生成时强约束的旧动作范围通常长于最终trim掉的范围，不能据此认定它就是失败原因。后续不能直接拿实际delay作为线上生成输入：它在推理结束时才确定。
